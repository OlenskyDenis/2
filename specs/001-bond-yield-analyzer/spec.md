### Session 2026-09-24

- Q: Як саме організувати оновлення та структуру аркушів у файлі Excel при повторних запусках збору котирувань? (FR-006) → A: Варіант A: Три окремі аркуші — «Актуальні котирування» (один актуальний рядок на ISIN), «Історія котирувань» (новий зріз дописується вниз із міткою часу для фіксації динаміки) та «Графік виплат» (календар усіх купонів та сум погашення номіналу).
- Q: Як система повинна реагувати, якщо цільовий файл Excel заблоковано користувачем (наприклад, відкрито у програмі Microsoft Excel під час запуску збору)? (FR-004) → A: Варіант A: Зупинити процес і повідомити користувача про блокування файлу з вимогою закрити Excel та повторити спробу (Fail Fast, захист від створення розрізнених копій та порушення цілісності бази даних).
- Q: Якою має бути поведінка інтерфейсу командного рядка (CLI) при запуску інструменту без передачі додаткових параметрів? (FR-007) → A: Спрощений прямий запуск без прапорців: команда відразу збирає всі дані, оновлює файл bonds.xlsx у поточній папці та обов'язково транслює в консоль зрозумілий покроковий прогрес для кожного етапу (підключення, отримання сесії, вивантаження каталогу, вилучення графіків виплат, збереження в Excel, підсумок).
- Q: Які алгоритмічні захисти надійності повинні діяти на кожному кроці виконання (Failure Modes & Edge Cases)? → A: Комплексний захист пайплайну: перевірка прав на запис перед стартом; повторні спроби (retry) при короткочасних мережевих збоях; автооновлення сесії при session_was_expired; мікро-троттлінг запитів (~50-100 мс) проти блокування за частоту; часткова відмовостійкість (збій графіка 1 паперу не перериває збір решти); атомарне збереження Excel через .tmp файл із наступним безпечним перейменуванням (гарантія від пошкодження бази даних); примусовий UTF-8 вивід у термінал.
- Q: Як саме вилучати залишок облігацій у продажу («мін 1 макс 85217 шт.» / «в наявності 0») та організувати безпечний збір даних без ризику блокування IP? (FR-002, FR-010) → A: Двоетапний публічний збір без авторизації. Етап 1 — один POST-запит до каталогу (`action: bargaining`) повертає всі 40 активних ISIN з цінами та ставками. Етап 2 — послідовні швидкі GET-запити до кожного паперу: `action=limits&operation=s` (повертає точну кількість облігацій у продажу `count`, статус активності `active` та ліміти сум) і `action=operations` (графік купонів) із мікропаузою 50–100 мс. Це гарантує 100% збереження залишків у наявності та захищає IP від блокування за спам.
- Q: Як система повинна оновлювати аркуш «Графік виплат» та додавати записи до «Історії котирувань» при повторних запусках? (FR-005, FR-006) → A: Гібридна неруйнівна модель: 1) В «Історії котирувань» новий зріз додається при зміні цін чи залишку (дублікати ідентичних рядків за той самий день не плодяться); 2) В «Графіку виплат» застосовується неруйнівне злиття (upsert за ключем ISIN+Дата+Тип): нові дати додаються, але якщо виплата минула або прибрана банком — рядок з Excel НЕ видаляється, зберігаючи повну історію виплат; 3) На аркуші «Актуальні котирування» папери, що зникли з каталогу банку, не видаляються, а позначаються статусом «Знято з торгів / Погашено».
- Q: Як система повинна вчинити зі збереженням у файл Excel, якщо під час циклічного опитування 40 випусків стався невідновлюваний збій мережі на середині процесу (наприклад, успішно опитано 25 із 40 паперів)? (FR-009, FR-011) → A: Варіант A: Принцип транзакційної цілісності («все або нічого»). Якщо повний збір перервано через мережевий обрив, цільовий файл Excel bonds.xlsx не модифікується взагалі (транзакція скасовується, тимчасовий файл .tmp видаляється), а в stderr/консоль виводиться чітке повідомлення про збій зв'язку з пропозицією повторити запуск. База даних зберігається в узгодженому стані без розсинхронізованих напівзрізів.
- Q: За яким порядком сортування система повинна розташовувати рядки облігацій на аркушах Excel за замовчуванням? (FR-006) → A: Природний порядок API + автофільтри Excel: дані записуються у природній послідовності, як їх повертає сервіс банку без примусового пересортування, а на всіх аркушах Excel для рядка заголовків автоматично вмикаються стандартні інтерактивні фільтри (Excel AutoFilter), щоб користувач міг у будь-який момент відсортувати або відфільтрувати рядки за будь-яким стовпчиком (за валютою, дохідністю, залишком чи датою).
- Q: Як система повинна вчинити з наявним файлом bonds.xlsx, якщо користувач запускає збір у неробочий час (вихідні дні, нічні години) або під час регламентних робіт, коли сервіс банку повертає 0 доступних паперів у каталозі? (FR-001, FR-005) → A: Варіант A: Захист бази від затирання порожніми даними. Якщо каталог повертає 0 облігацій (торгова сесія закрита або регламентні роботи), файл bonds.xlsx залишається недоторканим (раніше збережені котирування не перезаписуються порожнім списком), а в консоль виводиться інформаційне сповіщення про закриті торги із збереженням наявного робочого зрізу.
- Q: Якою має бути поведінка точки входу CLI щодо шляху до цільового файлу Excel: жорстко зафіксувати лише ./bonds.xlsx чи підтримувати необов'язковий шлях із ./bonds.xlsx за замовчуванням? (FR-004, FR-007) → A: Варіант A: Необов'язковий аргумент із дефолтом. При запуску без параметрів система зберігає/оновлює ./bonds.xlsx у поточній папці. За потреби користувач або автоматизований тест може передати власний шлях до файлу (позиційним аргументом або прапорцем --output), який буде використано замість стандартного.
- Q: Як забезпечити максимально простий запуск для користувача Windows та як система має діяти при першому запуску без наявного файлу Excel? (FR-004, FR-007) → A: Запуск через bat-файл + автоматичне створення Excel з нуля: 1) У корені проекту створюється готовий файл run.bat, який дозволяє запустити збір подвійним кліком миші у Windows Explorer із командою pause наприкінці для спокійного перегляду підсумку; 2) Якщо цільовий файл bonds.xlsx відсутній, система автоматично створює нову робочу книгу з усіма 3 аркушами, стилями, шапками та автофільтрами без помилок.

## User Scenarios & Testing *(mandatory)*


### Користувацька історія 1 - Збір повного каталогу облігацій, графіків виплат та залишків у наявності (Пріоритет: P1)

Як інвестор, я хочу запустити команду збору даних, щоб система автоматично звернулася до джерела (першочергово Приват24), отримала актуальний список усіх облігацій, їхні ціни купівлі/продажу, заявлені дохідності, строки погашення, залишок паперів у вільному продажу (у штуках) та повні графіки виплати купонів.

**Чому цей пріоритет**: Це базовий функціонал першого етапу проекту, без якого неможливо сформувати інформаційну базу для прийняття рішень та відстежувати дефіцит або вичерпання випусків.

**Незалежний тест**: Запуск команди збору даних для джерела Приват24 повертає повну структуровану колекцію паперів (усі доступні гривневі, доларові та євро-облігації) із валідними числовими показниками цін, точними залишками в наявності (шт.), статусом продажу та масивами купонних виплат.

**Сценарії прийняття**:

1. **Given** доступність інтернет-з'єднання та сервісу джерела, **When** користувач ініціює команду збору даних, **Then** система успішно отримує всі активні випуски облігацій (ISIN, валюта, дата погашення, ціна купівлі з НКД, дохідність купівлі, ціна продажу банку за наявності, статус військової облігації, точний залишок у продажу в штуках `count`, статус активності `active`, ліміти сум та повний графік виплат).
2. **Given** тимчасова недоступність веб-ресурсу або помилка мережі, **When** виконується збір, **Then** система коректно завершує процес із ненульовим кодом помилки та зрозумілим повідомленням у `stderr` без пошкодження наявних збережених даних.

### Користувацька історія 2 - Збереження та накопичення історії в Excel як базі даних (Пріоритет: P1)

Як інвестор, я хочу, щоб зібрані котирування автоматично зберігалися в файл Excel (`.xlsx`), де фіксуватиметься дата і час кожного зрізу, а нові дані додаватимуться до історії, не перетираючи попередні спостереження.

**Чому цей пріоритет**: Excel виступає прозорою, зручною для користувача базою даних, яка зберігає історичні зрізи для подальшого аналізу трендів, порівняння динаміки цін та темпів розкуповування випусків.

**Незалежний тест**: Виконання двох послідовних зборів котирувань формує в Excel-файлі історію записів із мітками часу, де кожен папір має відповідні зрізи вартості, залишки на момент спостереження та повний графік майбутніх грошових потоків.

**Сценарії прийняття**:

1. **Given** відсутність попереднього Excel-файлу, **When** завершується збір даних, **Then** система створює новий структурований файл Excel із чіткими заголовками колонок, форматуванням чисел/дат та трьома аркушами: «Актуальні котирування» (поточний зріз із залишком шт. та статусом активності), «Історія котирувань» (хронологічний реєстр зміни цін та залишків) та «Графік виплат» (повний розклад купонів і погашень за кожним ISIN).
2. **Given** наявний Excel-файл із попередніми даними, **When** користувач повторно запускає команду збору, **Then** система оновлює аркуш «Актуальні котирування», додає новий історичний зріз із поточною міткою часу до «Історії котирувань» та синхронізує «Графік виплат», зберігаючи всі попередні записи.

### Користувацька історія 3 - Модульні точки розширення (заглушки під майбутні цикли) (Пріоритет: P2)

Як інженер та користувач, я хочу мати чітко закладені інтерфейси (заглушки) для підключення нових сайтів (брокери/біржі), автоматичного планувальника оновлень за розкладом та модуля розрахунку реальної прибутковості, щоб у наступних циклах легко додати аналітику без переписування ядра.

**Чому цей пріоритет**: Забезпечує принципи простоти та модульності (Library-First), дозволяючи завершити перший цикл збору даних без надлишкової складності (YAGNI), але з гарантією масштабованості.

**Незалежний тест**: Перевірка наявності чітко визначених контрактних інтерфейсів у коді (для нових провайдерів джерел, планувальника задач та розрахункового рушія).

**Сценарії прийняття**:

1. **Given** базова бібліотека збору даних, **When** модуль розширення реалізує контракт джерела даних, **Then** нова платформа може бути зареєстрована без модифікації коду роботи з Excel.
2. **Given** запуск CLI-команди з прапорцем виклику аналітики чи планувальника, **When** ці можливості викликаються, **Then** система повідомляє про статус заглушки та очікування реалізації в наступному циклі.

### Граничні випадки (Edge Cases)

- **Відсутність прав на запис у директорії**: перевіряється на першому кроці перед мережевими запитами (Fail Fast) з чітким діагностичним повідомленням.
- **Блокування файлу Excel користувачем**: якщо `bonds.xlsx` відкрито у Microsoft Excel, система негайно зупиняє запис із ненульовим кодом помилки та виводить у `stderr` повідомлення з вимогою закрити програму (без створення хаотичних копій).
- **Збої мережі та технічні роботи в банку (502/503/504)**: запити мають таймаут 10 секунд та до 2 повторних спроб (retry) перед поверненням діагностичної помилки у `stderr`.
- **Застарівання гостьової сесії (`session_was_expired`, код 95)**: система автоматично ініціалізує нову гостьову сесію `init` та повторює дію без збою для користувача.
- **Порожній каталог котирувань (вихідні дні, закриття торгів, регламентні роботи)**: якщо сервер повертає 0 облігацій, система виводить у консоль зрозуміле повідомлення про закриті торги та повністю зберігає наявний файл `bonds.xlsx` без жодних змін (захист бази від затирання порожніми таблицями).
- **Обмеження частоти запитів (Rate Limiting / 429)**: застосовується безпечний двоетапний збір (1 запит каталогу + 40 пар запитів `limits` та `operations` із мікро-троттлінгом ~50-100 мс між викликами), що сумарно триває ~3-5 с і повністю виключає блокування IP-адреси за спам.
- **Повне розпродавання / нульовий залишок випуску (`count = "0"` або `active = false`)**: фіксується зі значенням 0 шт. та статусом «Розкуплено / Недоступно» замість помилки або пропуску рядка, що дозволяє інвестору фіксувати точний момент вичерпання випуску.
- **Частковий збій на одному випуску (помилка 500 для графіка чи лімітів)**: збій отримання додаткових даних для одного паперу не перериває роботу; система фіксує попередження в лозі та успішно зберігає котирування для всіх інших 39 паперів (Graceful degradation).
- **Відсутність ціни зворотного викупу (`sellPrice = null`)**: фіксується як порожнє значення, сигналізуючи про відсутність дострокового викупу банком.
- **Різні валюти (UAH, USD, EUR)**: зберігаються з обов'язковою фіксацією коду валюти, запобігаючи змішуванню грошових потоків.
- **Аварійне переривання під час запису (Ctrl+C, збій живлення)**: файл пишеться спочатку у `.bonds.xlsx.tmp` і лише після повної валідації замінює основний файл, виключаючи ризик пошкодження або обнулення файлу.
- **Невідновлюваний обрив зв'язку посеред опитування (частковий збір)**: застосовується сувора транзакційність («все або нічого»). Якщо під час опитування 40 випусків стався обрив зв'язку і вичерпані спроби retry, цільовий файл `bonds.xlsx` не модифікується (транзакція скасовується, тимчасовий `.tmp` файл очищується), а користувач отримує чітке повідомлення про збій у `stderr` із пропозицією повторити запуск. Це виключає появу неповних напівзрізів і розсинхронізації в базі даних.

## Вимоги *(mandatory)*

### Функціональні вимоги

- **FR-001**: Система ПОВИННА виконувати автоматичне вилучення даних про облігації з сервісу Приват24 через гостьову сесію без необхідності введення логіна та пароля користувача.
- **FR-002**: Система ПОВИННА збирати повний набір доступних атрибутів для кожної облігації:
  - Унікальний код ISIN;
  - Валюта (UAH, USD, EUR);
  - Дата остаточного погашення;
  - Залишковий термін до погашення;
  - Ознака військової облігації (так/ні);
  - Ціна купівлі клієнтом (включаючи накопичений купонний дохід);
  - Заявлена банком дохідність купівлі (річний %);
  - Ціна продажу банку (якщо доступна на вторинному ринку);
  - Дохідність продажу (якщо доступна);
  - Тип розрахунку дохідності банку (`SIM` / `YTM`);
  - Залишок паперів у наявності у продажу в банку (кількість штук `available_count`, параметр `count` з ендпоінту `limits`);
  - Статус доступності випуску для купівлі (`active`: відкритий/закрито/розкуплено);
  - Ліміти сум угоди банку (`minAmount`, `maxAmount`).
- **FR-003**: Система ПОВИННА отримувати вичерпний графік виплат (`operations`) для кожного паперу: дата кожної майбутньої купонної виплати, розмір купона в грошових одиницях, дата та сума погашення номіналу.
- **FR-004**: Система ПОВИННА зберігати зібрані дані у локальний файл Microsoft Excel (`.xlsx`) за вказаним або стандартним шляхом (`./bonds.xlsx`). Якщо файл відсутній на момент запуску, система ПОВИННА автоматично створити нову книгу Excel з повною схемою з трьох аркушів («Актуальні котирування», «Історія котирувань», «Графік виплат»), відформатованими заголовками, числовими типами даних та активованими автофільтрами без жодних збоїв чи ручних дій користувача. Якщо файл уже існує — система виконує його оновлення згідно з правилами неруйнівного збереження історії.
- **FR-005**: Система ПОВИННА вести облік історії котирувань: кожна операція збору фіксує точну дату та час створення зрізу (Timestamp), додаючи новий запис в історію котирувань паперу (включаючи історію зміни залишку паперів у продажу). Для запобігання надлишковому роздуванню таблиці дублікатами діє правило дедуплікації: новий запис в «Історію котирувань» додається лише тоді, коли змінилася ціна купівлі, ціна викупу або кількість у наявності (або коли це перший збір за поточну добу). Якщо запуск повторний за день і всі показники ідентичні — дублікат не створюється, а лише актуалізується час останньої перевірки на аркуші «Актуальні котирування».
- **FR-006**: Структура Excel-файлу ПОВИННА включати три обов'язкові аркуші зі строгою схемою колонок та неруйнівною логікою оновлення:
  - **Аркуш «Актуальні котирування»**: останній зріз за кожним ISIN. Якщо облігація зникає з торгів банку (розкуплена або погашена), вона не видаляється з таблиці, а переводиться у статус `Знято з торгів / Погашено`. Колонки:
    1. `ISIN` (код цінного паперу)
    2. `Назва` (найменування випуску)
    3. `Валюта` (`UAH`, `USD`, `EUR`)
    4. `Дата погашення` (дата формату YYYY-MM-DD)
    5. `Днів до погашення` (ціле число)
    6. `Військова облігація` (Так / Ні)
    7. `Ціна купівлі (з НКД)` (число, 2 знаки після коми)
    8. `Дохідність купівлі (% річних)` (число, відсоток)
    9. `Ціна зворотного викупу банком` (число або порожньо, якщо викуп відсутній)
    10. `Дохідність викупу (% річних)` (число або порожньо)
    11. `Залишок у наявності (шт.)` (ціле число `count` або 0 при розкупленості)
    12. `Статус продажу` (`Активний` / `Розкуплено або недоступно` / `Знято з торгів / Погашено`)
    13. `Мін. сума угоди` (число `minAmount`)
    14. `Макс. сума угоди` (число `maxAmount`)
    15. `Час останнього зрізу` (дата й час YYYY-MM-DD HH:MM:SS)
  - **Аркуш «Історія котирувань»**: хронологічний часовий ряд зрізів для аналізу динаміки цін і темпів розпродажу залишків. Колонки:
    1. `Час зрізу` (Timestamp YYYY-MM-DD HH:MM:SS)
    2. `ISIN`
    3. `Валюта`
    4. `Ціна купівлі`
    5. `Дохідність купівлі (%)`
    6. `Ціна зворотного викупу`
    7. `Дохідність викупу (%)`
    8. `Залишок у наявності (шт.)`
    9. `Статус продажу`
  - **Аркуш «Графік виплат»**: структурований календар грошових потоків. Застосовується неруйнівне злиття (upsert за ключем `ISIN + Дата виплати + Тип виплати`): нові виплати додаються, наявні оновлюються, але якщо виплата минула чи сервер банку прибрав її з актуальних списків — запис із таблиці **НЕ видаляється**, забезпечуючи довічне збереження повної історії виплат. Колонки:
    1. `ISIN`
    2. `Валюта`
    3. `Дата виплати` (YYYY-MM-DD)
    4. `Тип виплати` (`Купон` або `Погашення номіналу`)
    5. `Сума виплати на 1 папір` (число, грошовий еквівалент)
    6. `Статус виплати` (Майбутня / Здійснена)
  - **Інтерактивність таблиць (AutoFilter)**: генератор Excel ПОВИНЕН активувати стандартні автофільтри (Excel AutoFilter) на рядках заголовків усіх трьох аркушів, зберігаючи природний порядок надходження даних від джерела та надаючи користувачеві можливість миттєво сортувати і фільтрувати дані за будь-яким параметром безпосередньо у програмі Excel.
- **FR-007**: Інструмент ПОВИНЕН надавати гранично простий інтерфейс командного рядка (CLI) для запуску однією командою без обов'язкових прапорців. За замовчуванням цільовий файл створюється або оновлюється як `bonds.xlsx` у поточній робочій директорії. Інструмент ПОВИНЕН підтримувати передачу необов'язкового шляху до файлу Excel (позиційним аргументом або через прапорець `--output <шлях>`) для підтримки кастомних каталогів та ізоляції автоматизованих тестів. Для забезпечення швидкого та легкого запуску користувачем у середовищі Windows без необхідності відкриття термінала та ручного введення команд проект ПОВИНЕН містити командний файл швидкого запуску `run.bat` у корені репозиторію; подвійний клік на `run.bat` автоматично запускає процес збору, виводить зрозумілий покроковий прогрес у вікно консолі та завершується паузою (`pause`), щоб користувач міг спокійно переглянути підсумок перед закриттям вікна.
- **FR-008**: Система ПОВИННА містити модульні абстракції (заглушки/інтерфейси) для:
  - Підключення альтернативних джерел даних (нових сайтів/брокерів);
  - Автоматичного оновлення за розкладом (фонового планувальника);
  - Аналітичного модуля розрахунку фактичного заробітку та ранжування (заплановано на наступні цикли).
- **FR-009**: Система ПОВИННА виконувати збереження файлу Excel атомарно (запис у тимчасовий файл `.bonds.xlsx.tmp` з подальшим безпечним заміщенням `bonds.xlsx`), щоб унеможливити пошкодження або обнулення файлу при раптовому перериванні процесу.
- **FR-010**: Система ПОВИННА забезпечувати мережеву стійкість та захист від блокування IP-адреси за спам:
  - Двоетапна стратегія запитів: 1 POST-запит до каталогу `bargaining` для миттєвого завантаження всіх 40 паперів, після чого послідовні точкові запити `limits` (`operation=s`) та `operations` для кожного випуску;
  - Мікро-троттлінг із плаваючою затримкою (~50-100 мс) між запитами до окремих випусків (сумарне навантаження розподілене на 3–5 секунд, що виглядає для сервера як звичайний людський перегляд сторінок);
  - Мережеві таймаути (10 с) та до 2 повторних спроб (retry) при короткочасних мережевих тайм-аутах;
  - Автоматичне оновлення сесії при помилці 95 (`session_was_expired`).
- **FR-011**: Система ПОВИННА підтримувати принцип часткової стійкості (Graceful degradation): тимчасова помилка завантаження графіка або залишку окремого паперу не зупиняє весь пайплайн, а фіксує попередження та зберігає котирування для всіх успішних випусків.
- **FR-012**: Система ПОВИННА зберігати котирування зі суворою типізацією Excel (числові значення для цін і ставок, дати формату ISO/Excel) та запобігати появі дублікатів зрізів для одного ISIN за один і той самий інтервал часу.
- **FR-013**: CLI-інструмент ПОВИНЕН примусово ініціалізувати UTF-8 кодування потоків введення/виведення для коректного відображення української мови в терміналах будь-яких ОС.

### Ключові сутності (Key Entities)

- **Облігація (Bond)**: Базовий опис цінного паперу (ISIN, валюта, дата погашення, ознака військової облігації, залишок у наявності в банку у штуках, статус активності продажу).
- **Котирування зрізу (Price Snapshot)**: Дані вартості паперу в певний момент часу (мітка часу збору, ціна купівлі, ціна викупу банку, спред, заявлена банком ставка, залишок штук у продажу на момент зрізу).
- **Подія грошового потоку (Cash Flow Event)**: Запланована виплата (дата виплати, тип події — купон або повернення номіналу, грошова сума у валюті випуску).
- **Репозиторій збереження Excel (Excel Storage)**: Компонент збереження даних, що керує структурою книги, атомарним записом, накопиченням історичних рядків та форматуванням колонок.
- **Адаптер джерела даних (DataSource Adapter)**: Інтерфейс підключення веб-ресурсів (реалізований провайдер Приват24 + інтерфейсна заглушка для майбутніх джерел).

## Критерії успіху *(mandatory)*

### Вимірювані результати

- **SC-001**: Повний цикл вилучення даних за всіма доступними випусками Приват24 (40+ облігацій разом із графіками купонів) та збереження в Excel виконується менш ніж за 10 секунд при звичайному інтернет-з'єднанні.
- **SC-002**: Згенерований файл Excel (`.xlsx`) коректно відкривається в офісних редакторах (Microsoft Excel, LibreOffice, Google Таблиці), містить правильні формати числових даних (грошові, процентні, календарні дати) без втрати точності копійок.
- **SC-003**: 100% активних облігацій каталогу зберігаються із прив'язаними графіками купонів, датами погашення та точними залишками паперів у наявності (шт.).
- **SC-004**: Повторні запуски збору даних детерміновано додають нові записи до історії котирувань без виникнення дублікатів чи спотворення раніше збереженої історії.
- **SC-005**: 100% збереження цілісності бази даних Excel навіть при примусовому перериванні програми користувачем (Ctrl+C) під час збереження завдяки механізму атомарного запису.

## Припущення (Assumptions)

- Дані вилучаються через публічне гостьове API каталогу Приват24 без необхідності двофакторної автентифікації користувача.
- Збереження виконується у форматі `.xlsx` локально на комп'ютері користувача.
- На цьому першому етапі аналітичні розрахунки чистої прибутковості не блокують реліз: ядро фокусується суто на бездоганному зборі вичерпних даних і наповненні таблиці Excel.
- Інтерфейси для нових сайтів та автоматичного планувальника проектуються на рівні архітектури, щоб забезпечити безшовне масштабування в наступних ітераціях.
